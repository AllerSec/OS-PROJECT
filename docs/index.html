01 · Motivation

Why synchronization in RTOS?

In a real-time system, several tasks share buffers, devices, counters and queues. When two of them touch the same data without coordination, the result is silently wrong, the system deadlocks, or a high-priority task misses its deadline. Linux gives us the tools to prevent this — but each one comes with trade-offs.

The problem

Concurrent threads can interleave at any byte boundary. A simple counter += 1 is not atomic — it is read, modify, write, and another thread can sneak in between the read and the write. The bug does not crash; it just produces wrong numbers, and only sometimes.

The toolkit

Linux exposes mutexes, spinlocks, semaphores, read-write locks, condition variables and priority-inheritance mutexes. Picking the right one for the right context is the difference between a system that meets its deadlines and one that silently loses data.

Goal of this project: build an interactive web app that lets you see each of these tools in action — including the bugs they prevent — so the difference between them is no longer abstract.
02 · Concepts

Six concepts, one page

Each demo below isolates one concept and lets you trigger it on demand. The numbers you see are real measurements, not fake values.

  1. Race conditionTwo threads on one variable. Without a mutex, updates are lost.
  2. MutexOne thread at a time. Blocked threads sleep until the lock is free.
  3. SpinlockOne thread at a time, but blocked threads burn CPU until the lock is free.
  4. SemaphoreCounts a resource (free slots, ready items). Blocks at zero.
  5. Read-Write lockMany readers in parallel; one exclusive writer. Writer-priority avoids starvation.
  6. DeadlockCircular wait between threads. Fixed with a global lock-order rule.
  7. Priority inversionA high-priority task indirectly blocked by a medium one — the boss problem.
  8. Priority inheritanceThe lock holder temporarily inherits the priority of the highest waiter.
  9. Atomics & futexLock-free primitives that mutexes are built on top of.

01 Race condition

Two threads, one counter. With and without a mutex.

What is this?

A race condition happens when two threads change the same data at the same time and one update gets lost. It does not crash, but the result is wrong.

Each thread runs counter += 1 many times. Without a lock, both threads can read the same old value, add one, and write it back — the final number is too small.

A mutex (mutual exclusion) makes only one thread at a time enter the section that touches the shared data. With it, the result is exact.

02 Mutex vs spinlock

Same workload, two locking strategies.

What is this?

A mutex makes blocked threads sleep until the lock is free. A spinlock makes them busy-wait in a tight loop, burning CPU until the lock is free.

Spinlocks are faster when the critical section is shorter than a context switch (a few microseconds). Mutexes are better when the section is longer, because sleeping releases the CPU.

We run the exact same job with each, and graph the time. The Linux kernel uses both, depending on context — you cannot sleep inside an interrupt handler, so spinlocks rule there.

03 Producer / consumer

Bounded buffer with two semaphores plus a mutex.

What is this?

A classic pipeline. The producer makes items, the consumer uses them. Between them sits a buffer of fixed size.

Two semaphores count free slots and ready items, and a mutex protects the buffer itself. The producer cannot overflow; the consumer cannot read empty slots.

This is how device drivers, network stacks, and audio pipelines move data between threads in Linux.

05 Deadlock

Two threads, two locks, opposite order.

What is this?

A deadlock is a circular wait. Thread A holds lock 1 and wants lock 2. Thread B holds lock 2 and wants lock 1. Neither ever continues.

The fix is a global lock order: every thread always grabs lock 1 before lock 2. No cycle can form.

A real-time system that deadlocks misses its deadline. Real kernels use lock hierarchies and runtime checks (lockdep) to avoid this.

06 Priority inversion

A high-priority task blocked by a medium one.

What is this?

Three threads — Low, Medium, High. Low holds a mutex. High wakes up and waits for it. Medium is CPU-bound and pre-empts Low. Now High waits for Low, which waits for Medium. This is priority inversion.

Priority inheritance fixes it: when High blocks on the mutex, Low temporarily inherits High's priority. Medium can no longer pre-empt Low; the mutex is released quickly. Linux supports this with PTHREAD_PRIO_INHERIT.

Real OS-level priority inheritance needs Linux. We model the effect with a cooperative scheduler so the visual difference is clear on any platform.

05 · Conclusions

What we learned

Building each demo from scratch made the trade-offs concrete. Here is what stands out.

Mutex vs spinlock is contextual

Spinlocks win for ultra-short critical sections; mutexes win when the section is longer than a context switch. Linux uses both — spinlocks inside interrupt handlers (where sleeping is forbidden), mutexes in user space.

Deadlocks are structural

A deadlock is rarely a "missing lock"; it is a circular dependency between locks. The fix is a global ordering rule applied everywhere, not a clever runtime check at one site.

Priority inheritance is essential

Without it, an unrelated medium-priority task can make a high-priority task miss its deadline. The Mars Pathfinder bug was exactly this. Linux fixes it with PTHREAD_PRIO_INHERIT.

The browser is a real OS

Web Workers + SharedArrayBuffer + Atomics let us run real concurrent code in a static page. The same algorithm runs identically on Linux pthreads and on the browser — the synchronisation theory is portable.
